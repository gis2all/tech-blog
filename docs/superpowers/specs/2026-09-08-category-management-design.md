# 后台分类管理设计

## 目标

在 Decap CMS 后台增加与标签页同级的分类管理页。分类页直接在主区域提供分类搜索、筛选、排序、新增、重命名/合并和删除，不进入二级编辑页面。

分类是文章的单值受控字段。分类编辑器和分类管理页共用同一份分类库，避免 `config.yml`、文章 frontmatter 和后台列表发生漂移。

## 数据模型

新增 `src/data/category-library.json`，结构为：

```json
{
  "categories": ["x402", "DevOps", "Crypto"]
}
```

该文件是分类名称的唯一事实源。初始内容从当前 `public/admin/config.yml` 的分类选项迁移，并保留未提交的 `Crypto` 改动。

文章的 `category` 字段改用 `category_selector` 自定义 Decap widget，从分类库读取单值选项。`config.yml` 不再重复维护分类 options，但保留分类集合定义，以便 Decap 查询分类库文件和渲染后台导航。

## 后台页面

路由为 `#/collections/categories`，左侧导航位于“标签”之后、“专题”之前。页面布局沿用标签页的主区域壳层和现有设计 token：

- 标题、分类总数和未使用数量；
- 分类搜索；
- 全部、已使用、未使用筛选；
- 按名称、按使用量排序；
- 新增分类按钮；
- 分类、使用情况、操作三列列表；
- 重命名/合并和删除操作；
- 加载、保存、失败、空结果和确认状态。

分类正在被文章使用时，删除按钮禁用并显示使用数量。所有管理操作留在分类主页面，不新增分类二级编辑页。

## 领域与持久化

`public/admin/category-domain.js` 提供纯逻辑：名称规范化、去重、使用统计、列表筛选/排序、删除条件和重命名计划。

`public/admin/category-operations.js` 负责文章 frontmatter 的分类读取/替换、重命名计划生成和原子持久化数据组装。重命名到已有分类时按合并处理，把源分类文章迁移到目标分类并移除源分类；重命名到新名称时只替换名称。删除操作在前端展示禁用状态后仍需重新读取文章使用情况再写入。

所有涉及分类库与文章的写入都调用现有 `__persistEditorialTransaction`，一次提交全部数据文件，失败时不留下部分更新。

## 编辑器与配置

- `config.yml` 的文章分类字段改为 `category_selector`，配置分类集合文件 `src/data/category-library.json`。
- `index.html` 按现有脚本顺序加载分类 domain、selector 和 operations；分类 selector 只允许选择分类库中的值，不在文章编辑器内隐式创建分类。
- 分类集合被后台壳层接管，原生文件编辑器内容隐藏，避免出现第二套分类编辑入口。
- 分类名称继续要求非空、去首尾空白；比较采用现有字符串语义，不自动折叠大小写。

## 测试策略

- Vitest：覆盖分类 domain、frontmatter 读取/替换、重命名/合并计划和删除边界。
- CMS 契约测试：验证分类库文件、分类 selector、分类集合、导航标签和字段配置存在且不重复维护静态 options。
- Playwright：用时间戳分类和草稿夹具验证新增、重命名/合并、删除未使用分类；不依赖真实文章数量或固定文章名称。
- 后台 Axe：把 `#/collections/categories` 加入严重/致命违规为 0 的页面集合。

## 非目标

- 不改变前台分类 URL、分类页渲染和文章内容语义。
- 不新增数据库、认证流程、分类层级或多人审批。
- 不把分类管理拆成单独的二级编辑界面。
