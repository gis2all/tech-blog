## 1. 项目到底是什么

### 1.1 三层结构

HarmonicAgent 不是单一应用，而是三层叠加：

```
第一层：$HARMONIC 代币（Robinhood Chain 上的 Meme 币）
        ↓ 交易产生手续费
第二层：飞轮引擎（Collector → Agent → 回购销毁/RWA 分发/LP/储备）
        ↓ 机制可复用
第三层：Agent 工厂 + 一整套产品矩阵（Solve / 发射台 / 计算市场 / H10 指数 / 交易台）
```

**最关键的一点**：代币本身在合约层面没有收益权（Terms 明确写"Meme 币、不拥有收入或资产"）。飞轮是**运营方在链下的程序**，不是代币合约里写死的逻辑。这决定了整个项目的信任模型。

### 1.3 与普通 Meme 币的本质区别

普通 Meme：合约 + 社群 + 叙事。

后者更"真"，但不代表更"安全"——**它把风险从"合约能不能跑路"转移到了"运营方会不会、能不能、值不值得作恶"。**

## 3. Agent 工厂到底"是什么"

很多人把 Agent 工厂理解成"发币机器人"，这是误读。准确说法：

**Agent 工厂 = 把你的交易意图编译成一段受约束的自动执行程序，并给它一个独立钱包。**

### 3.1 三种 Agent 类型（官方定义）

| 类型 | 做什么 | 约束本质 |
|---|---|---|
| Treasury Agent | 持有你指定的资产组合并维持形状 | 仓位上限 + 再平衡 |
| Buyback Agent | 按节奏买某个代币并销毁（或持有） | 周期/日上限 + 储备金 |
| DCA Agent | 按周期定投，按错位/波动/深度/风险动态调仓 | 固定预算 + 风控 |
| Mining Agent | 跨 SLVR 网格 25 格下注，拿回 88% + 分润 | 每周期/每日上限 + 储备 |

### 3.2 当前唯一的活跃实例（真实数据）

```
ID: 862d28
类型: Mining Agent
状态: active
钱包: 0x89e18259f071798BA207cC510E8893a2543F6927
Mandate: 跨 25 格下注；每周期 ≤0.02 ETH；每日 ≤2 ETH；
         保留 0.002 ETH 储备；每 15 分钟运行；SLVR 提纯后持有
已跑周期: 0
NAV: null
```

**诚实的解读**：工厂**结构完整、实例稀少、尚未产生可评估业绩**。

### 3.3 工厂的经济模型

```
部署费 0.005 ETH（一次性）  → 运营方
每笔成交 25 bps             → 运营方
标的自身交易费              → 归各自机制（如 Hookr 的 50%–80% 创作者费）
发射台服务费 2.50%          → 运营方
```

**论点**：这构成了"卖铲子"模式的收入来源，**不依赖代币价格上涨**。
**反论**：0.005 ETH 部署费 × 当前 3 个 Agent ＝ **0.015 ETH**，收入可以忽略；模型正确但规模为零。

## 4. 核心飞轮机制（拆到最细）

### 4.1 完整闭环

```
① 用户在 Pons 池交易 $HARMONIC
        ↓ 产生 1% 交易费
② Pons V2 Collector / LP Locker 累积手续费
        ↓ Pons keeper 定期 sweep
③ Agent 每约 10 分钟调用领取（claim），手续费进入 Agent 钱包
        ↓ 运营方链下分配器按权重切分
④ Burn（回购→死地址） / RWA（买股票代币→分发给持币者）
   / LP（补流动性） / Reserve（留存）
```

### 4.3 这个 5.99 ETH 差额必须单独强调

**这是本次调研最重要的新发现之一。**

- `/health` 的 `quotable` 字段自己写道：只认链上 15.83 ETH / 504 次；账本多记 5.99 ETH，**"that difference is NOT quotable"**
- 项目没有隐瞒这一点——它主动把差额标出来并不纳入报价，这体现了一定的财务诚实
- 但它同时意味着：**"累计领取 21.82 ETH"这个常被引用的数字，不能被链上独立验证**
- 可能原因（未证实）：早期记账口径不同、重复计数、人工认领未上账、扫描盲区或历史迁移

**结论**：引用飞轮规模时，应使用 **15.83 ETH（链上）**，而不是 21.82 ETH（账本）。

### 4.4 分配权重是"链下政策"，不是"链上强制"

- 最近实际分配：Burn 60% / Reserve 20% / LP 10% / RWA 10%
- Lean 证明的约束：Burn 下限 **30%**、上限 100%
- **但**：这套分配器是运营方的程序代码，**不是部署在链上、不可篡改的合约**
- 所以 Lean 证明的是"**如果程序按这个规格运行**，则属性成立"——它证明的是模型，不是运行时的链上强制执行

**这是理解本项目最关键的一句话。**

## 8. Proof / Lean 体系（本项目最独特、也最容易被误读的部分）

### 8.1 两套完全不同的"证明"

| 系统 | 内容 | 数量 | 性质 |
|---|---|---|---|
| **Lean 4（Harmonic Aristotle）** | 数学定理 + 协议不变量 | 42 条 machine-checked | 形式化验证 |
| **`/api/proofs`（引擎标 "qed"）** | JS 数值/穷举自检 | 33 项，0 失败，43ms | 运行时自检 |

两者常被混为一谈，必须区分：
- **Lean 证明的是"模型和规格"**
- **`/api/proofs` 是启动时的数值自检，不是形式化证明**

### 8.2 Lean 不变量样本（共 23 条，22 已证 + 1 排队）

| 不变量 | 内容 |
|---|---|
| `alloc-sum-exact` | 任意输入下四路权重精确合计 10000 |
| `alloc-burn-floor` | 回购权重永不低于 3000 bps（30%） |
| `alloc-conserves` | 拆分金额不丢不增 |
| `alloc-drift-favours-burn` | 取整余数一律归入 burn，只会多不会少 |
| `supply-non-increasing` | 在 {buy, burn, add-liquidity, distribute} 字母表上流通供应不增 |
| `index-mint-never-dilutes` | 索引份额铸造永不超过 pro-rata |
| `index-redeem-never-overpays` | 份额赎回永不超过应得 |
| `index-daily-cap` | 单窗口再平衡不超过期初余额 25% |

### 8.3 最关键的限制（Terms 自己承认）

1. 证明的是 **Lean 模型和规格**，不是部署字节码
2. **不是审计**，不保证避免损失
3. `supply-non-increasing` 的"不卖币"证明，本质是**在字母表里故意不定义 `sell` 操作**
4. 未验证项：`apery`、`gauss-sum`、`four-color`、`euler-identity`（42 proved / 4 未验证）
5. 41 个下载的 Lean 文件中**未发现 `sorry` / `admit` / `axiom` / `unsafe`**——这一点属实、含金量较高

### 8.4 如何正确评价

**该给的分数**：在一个 Meme 币项目里认真做形式化验证，是极罕见的；不定义 `sell` 反而主动暴露弱点也说明团队懂行。
**不该给的分数**：这不构成对**运行时行为**、**链下程序**、**私钥安全**、**经济安全**的任何保证。它证明的是"如果一切按规格执行"的**条件性属性**。

## 10. 托管、合规与隐私（风险最集中的区域）

### 10.1 Terms 关键原文含义

| 条款 | 含义 | 风险 |
|---|---|---|
| "`$HARMONIC` is a meme coin, has no claim on income or assets" | 代币无收益权 | 价值全靠市场情绪 |
| "Fee and buyback policies may be changed by the operator" | 费用/回购政策可改 | 飞轮可被调弱 |
| X / Telegram / Desk Wallet 由服务派生并持有私钥 | 服务托管 | **平台可控制资金** |
| "**It is not your key, and it is not non-custodial.**" | 自认托管 | 与 UI "non-custodial" 措辞冲突 |
| 浏览器钱包功能由用户自己签名 | 仅此部分自托管 | 边界必须看清 |
| 服务托管在 Railway | 中心化托管 | 单点故障 |
| 聊天文本发送给未公开名称的 LLM provider | 数据外流 | 隐私风险 |
| 无第三方审计 | 未审计 | 合约/程序风险未知 |

### 10.2 托管边界图解

```
【真正的非托管】连自己的浏览器钱包 → 自己签名
【服务托管】X 登录 / Telegram / Desk Wallet → 私钥在服务端
【完全托管】Agent 钱包（0x89e1… 等）→ 由服务派生和运作
```

**必须说清楚**：项目在 UI 里说 "non-custodial"，但 Terms 明确承认 Desk Wallet 不是。这两处措辞存在**实质冲突**，是尽调中必须标红的点。

### 10.3 RWA 合规层

- 股票代币发行方：Robinhood Assets (Jersey) Limited
- 状态：**未在美国证券法下注册**
- 项目措施：综合制裁地区屏蔽且不可豁免；用户自担辖区合规
- 美方用户需签 waiver

**这不是合规背书**，而是**把合规责任转移给用户**。持有这类资产碎片在多数辖区存在法律不确定性。

### 11.3 对抗性论证：如果我要攻击这个项目，我会怎么说

1. **"数学即机制"是话术升级**：40 多条 Lean 证明的是链下模型，运行时仍由匿名运营方控制，证明与资金安全之间隔着整条信任链
2. **飞轮的核心动作不可强制执行**：没有任何链上合约强制 Burn ≥ 30%；运营方明天改成 5% 也不会违反任何代码
3. **EOA 是最大单点**：所有 Agent 钱包都是 EOA，私钥在服务端；一次入侵 = 全部 Agent 资金
4. **账本可信度有缺口**：5.99 ETH（占链上领取量 38%）对不上，虽被主动标注，但说明记账系统不严密
5. **产品全线低采用**：Compute 0 任务、Brains 0 个、Managed LP null、Agent 工厂 1 活跃，说明需求未被验证
6. **策略全线亏损**：交易台 −0.029、跟单 −0.053、预测 −7.01，三个独立策略都是负的
7. **流动性太薄**："市值 $2M"建立在 $13.6 万深度上，一个中等规模的卖出就能砸穿

### 11.4 对抗性论证：如果我要为项目辩护，我会怎么说

1. **链上是真的**：合约已验证、无 owner、真实交易、真实销毁、真实分发，不是空气
2. **主动披露亏损**：亏损、失败策略、暂停原因、人工卖出、账本差额全部公开，罕见的财务诚实
3. **不卖币的约束**：虽然靠"不定义 sell"，但配合无 owner/无 mint，合约层确实干净
4. **锁仓无提款**：Pons Locker 源码验证过，没有 withdrawal
5. **飞轮高频运行**：2,498 周期、1,595 次买入、1,344 次销毁，不是一次性表演

7. **工厂模型合理**：卖铲子收入不依赖币价，商业逻辑成立（只是规模为零）

## 13. 结论与建议

### 13.1 一句话结论

**HarmonicAgent 是一个机制真实、透明度反常地高、但信任边界完全落在匿名运营方手里的高风险早期 AI+DeFi 实验。它的创新点（Lean 形式化验证 + 真实飞轮）值得观察，它的采用率（几乎全部产品接近零）和资金安全边界（EOA + 托管 + 未验证合约）不支持任何"稳健"判断。**

### 13.2 三类读者的不同建议（非投资建议）

**如果你只是研究 AI Agent × DeFi 机制设计**
→ 这是极好的样本。重点看：飞轮闭环、Agent 工厂 mandate 模型、Lean 不变量集、AI 主动披露亏损的行为。

**如果你在研究"如何评估这类项目"**
→ 把它当反面教材的正向案例：它会主动告诉你自己的弱点（账本差额、策略未证明、合约未验证）。学会读懂这些自我标注。

**如果你在考虑投入资金**
→ 需要明确知道：合约层干净 ≠ 系统安全。真正掌握资金和规则的，是匿名团队、服务端私钥、链下分配器和 4 份看不见源码的合约。任何投入应视为**可归零的实验性支出**。

### 13.3 最值得继续追踪的三条线索

1. **4 份未验证合约能否公开源码** —— 这是最大黑箱
2. **5.99 ETH 账本差额的成因** —— 这是财务可信度的试金石
3. **交易台/跟单策略能否在 30 天后转正** —— 这是"AI 是否有真本事"的唯一硬指标
